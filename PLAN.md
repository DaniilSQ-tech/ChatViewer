# План реализации ChatList

Поэтапный порядок действий по реализации программы на основании [PROJECT.md](PROJECT.md).

---

## Этап 1. Подготовка проекта

1. Привести структуру каталогов к целевой:
   ```
   ChatViewer/
   ├── main.py          # точка входа и GUI
   ├── db.py            # работа с SQLite
   ├── models.py        # логика моделей (нейросетей)
   ├── network.py       # HTTP-запросы к API
   ├── requirements.txt
   ├── .env.example     # шаблон переменных окружения для API-ключей
   └── data/            # каталог для файла БД (опционально)
   ```
2. Обновить `requirements.txt`: PyQt6, httpx (или requests), python-dotenv.
3. Создать `.env.example` с примерами имён переменных (`OPENAI_API_KEY`, `DEEPSEEK_API_KEY` и т.д.).
4. Добавить загрузку `.env` при старте приложения.

---

## Этап 2. Слой базы данных (`db.py`)

1. Реализовать инициализацию SQLite: создание файла БД, применение схемы из [DATABASE.md](DATABASE.md).
2. Добавить CRUD для таблицы `prompts` (создание, чтение списка, поиск по тексту/тегам).
3. Добавить CRUD для таблицы `models` (создание, редактирование, удаление, фильтр `is_active = 1`).
4. Добавить CRUD для таблицы `results` (запись выбранных результатов, чтение истории).
5. Добавить CRUD для таблицы `settings` (чтение/запись настроек по ключу).
6. Инкапсулировать все SQL-запросы внутри `db.py`; остальные модули обращаются только через его API.

---

## Этап 3. Логика моделей (`models.py`)

1. Описать dataclass или TypedDict для сущности «модель» (id, name, api_url, api_id, api_key_env, is_active, provider).
2. Реализовать загрузку списка моделей из БД через `db.py`.
3. Реализовать получение только активных моделей (`is_active = 1`).
4. Реализовать чтение API-ключа из переменной окружения по полю `api_key_env`.
5. Добавить валидацию: активная модель должна иметь заполненный ключ в `.env`.
6. Подготовить начальный набор моделей (seed) или UI для их добавления.

---

## Этап 4. Сетевой слой (`network.py`)

1. Выбрать HTTP-библиотеку (рекомендуется `httpx`) и базовый клиент с таймаутом.
2. Реализовать единый интерфейс отправки промта: `send_prompt(model, prompt_text) -> str`.
3. Добавить адаптеры под типы провайдеров (OpenAI-совместимый, DeepSeek, Groq и т.д.) — поле `provider` в таблице `models`.
4. Обработать ошибки сети и API: таймаут, 401, 429, пустой ответ — возвращать понятное сообщение вместо падения приложения.
5. *(Опционально)* Логировать каждый запрос (время, модель, статус, длительность) в файл или таблицу `request_logs`.

---

## Этап 5. Временная таблица результатов (в памяти)

1. Описать структуру строки временной таблицы: `model_name`, `model_id`, `response_text`, `selected`.
2. Реализовать класс или список в памяти для хранения текущей сессии запроса.
3. Реализовать методы:
   - `clear()` — очистка при новом промте;
   - `add_result(...)` — добавление ответа после запроса к API;
   - `get_selected()` — получение строк с `selected = True`;
   - `toggle_selected(row_index)` — переключение чекбокса.
4. Связать временную таблицу с текущим промтом (текст и/или `prompt_id`).

---

## Этап 6. Основной интерфейс — каркас (`main.py`)

1. Заменить заглушку на полноценное главное окно с вкладками или панелями:
   - **Запрос** — ввод промта и отправка;
   - **Результаты** — временная таблица ответов;
   - **История** — сохранённые результаты из БД;
   - **Модели** — управление нейросетями;
   - **Настройки** — параметры приложения.
2. Настроить меню, статусную строку (прогресс отправки, ошибки).
3. Подключить загрузку БД и `.env` при старте.

---

## Этап 7. Интерфейс ввода промта

1. Поле многострочного ввода для нового промта.
2. Выпадающий список или боковая панель с сохранёнными промтами из таблицы `prompts`.
3. Поле тегов (при сохранении промта в БД).
4. Кнопка **«Отправить»**:
   - сохранить промт в `prompts` (если новый);
   - очистить временную таблицу;
   - запустить параллельную или последовательную отправку во все активные модели;
   - заполнить временную таблицу ответами;
   - обновить экран результатов.
5. Индикатор загрузки на время ожидания ответов от API.

---

## Этап 8. Интерфейс результатов

1. Таблица (`QTableWidget` или `QTableView` + модель) с колонками:
   - чекбокс **selected**;
   - **название модели**;
   - **текст ответа** (с переносом строк, возможность прокрутки).
2. Кнопка **«Сохранить»**:
   - записать строки с `selected = True` в таблицу `results` через `db.py`;
   - очистить временную таблицу;
   - обновить вкладку «История».
3. Кнопка **«Снять выделение»** / **«Выбрать все»** (удобство).
4. При вводе нового промта — автоматически очищать временную таблицу до получения новых ответов.

---

## Этап 9. Управление моделями (GUI)

1. Таблица моделей: name, api_url, api_id, api_key_env, is_active.
2. Форма добавления/редактирования модели.
3. Переключатель активности (`is_active`) без удаления записи.
4. Проверка наличия ключа в `.env` при активации модели.

---

## Этап 10. История и настройки

1. **История** — таблица сохранённых результатов из `results` с привязкой к промту и модели.
2. Поиск и сортировка по колонкам (опционально, но желательно).
3. **Настройки** — редактирование записей таблицы `settings` (путь к БД, таймаут запросов, тема и т.д.).

---

## Этап 11. Дополнительные функции (опционально)

1. Экспорт выбранных результатов в **Markdown** и **JSON**.
2. Поиск и сортировка во всех таблицах GUI.
3. Логи запросов (файл `logs/` или таблица `request_logs`).
4. Поддержка новых провайдеров через добавление адаптера в `network.py`.

---

## Этап 12. Сборка и проверка

1. Прогнать сценарии вручную:
   - новый промт → ответы → сохранение выбранных;
   - выбор сохранённого промта → повторная отправка;
   - добавление/деактивация модели;
   - ошибка API (нет ключа, таймаут).
2. Обновить `build.ps1` / PyInstaller для сборки `.exe`.
3. Проверить, что `.env` не попадает в сборку и в git.

## Этап 13. AI-ассистент для улучшения промтов

План реализации функции из [PROJECT.md](PROJECT.md), раздел 7.

### Цель

Помочь пользователю улучшить промт перед массовой отправкой в несколько моделей: одна выбранная модель (OpenRouter) анализирует текст и предлагает улучшенные варианты.

### Зависимости

- Готовы: `network.py` (OpenRouter-клиент), `models.py`, `db.py` (`settings`), вкладка «Запрос» в `ui/main_window.py`.
- Новые модули: `prompt_assistant.py` (логика), `ui/prompt_assistant_dialog.py` (окно результатов).

---

### Этап 13.1. Настройки и выбор модели-ассистента

1. Добавить в таблицу `settings` ключи:
   - `assistant_model_id` — ID модели из таблицы `models`, используемой для улучшения промтов;
   - `assistant_enabled` — включён ли ассистент (`1` / `0`).
2. На вкладке **«Настройки»** добавить:
   - выпадающий список активных chat-моделей OpenRouter;
   - чекбокс «Использовать AI-ассистент».
3. Значение по умолчанию: первая доступная бесплатная chat-модель (например, `Ling-3.0-flash (free)`).
4. Валидация: если модель не выбрана или ключ отсутствует — кнопка «Улучшить промт» неактивна с подсказкой.

---

### Этап 13.2. Модуль `prompt_assistant.py`

1. Описать dataclass `PromptImprovementResult`:
   - `original: str` — исходный промт;
   - `improved: str` — улучшенная версия;
   - `alternatives: list[str]` — 2–3 варианта переформулировки;
   - `adaptations: dict[str, str]` — адаптации под тип задачи: `code`, `analysis`, `creative` (опционально, если модель вернула).
2. Реализовать системный промт-шаблон (константа `ASSISTANT_SYSTEM_PROMPT`), который инструктирует модель:
   - сохранить смысл и язык исходного текста;
   - вернуть ответ **строго в JSON**:
     ```json
     {
       "improved": "...",
       "alternatives": ["...", "...", "..."],
       "adaptations": {
         "code": "...",
         "analysis": "...",
         "creative": "..."
       }
     }
     ```
3. Реализовать класс `PromptAssistant`:
   - `improve(prompt_text: str, model: AIModel, network: NetworkClient) -> PromptImprovementResult`;
   - отправка через существующий `network.send_prompt()` (один запрос, одна модель);
   - парсинг JSON из ответа с fallback: если JSON битый — показать сырой текст как `improved`, альтернативы пустые.
4. Обработка ошибок: пустой промт, таймаут, ошибка API — возвращать понятное исключение или объект с полем `error`.

---

### Этап 13.3. Фоновый worker

1. Создать `ImprovePromptWorker(QThread)` в `workers.py`:
   - принимает `PromptAssistant`, модель, текст промта;
   - сигналы: `finished(PromptImprovementResult)`, `failed(str)`;
   - **не обращается к SQLite** из фонового потока (модель передаётся заранее, `log_requests=False`).
2. Блокировать повторный запуск, пока worker выполняется.

---

### Этап 13.4. UI — кнопка и окно результатов

1. На вкладке **«Запрос»** рядом с полем ввода добавить кнопку **«Улучшить промт»**.
2. При нажатии:
   - взять текст из `prompt_edit`;
   - если пусто — предупреждение;
   - показать индикатор загрузки в статусной строке;
   - запустить `ImprovePromptWorker`.
3. Создать `PromptAssistantDialog` (`ui/prompt_assistant_dialog.py`):
   - **Исходный промт** — read-only, сверху;
   - **Улучшенный** — read-only + кнопка **«Подставить»**;
   - **Альтернативы** — список (2–3 пункта), у каждого кнопка **«Подставить»**;
   - **Адаптации** (если есть) — вкладки или группа: «Код», «Анализ», «Креатив» + кнопки **«Подставить»**;
   - кнопка **«Закрыть»**.
4. **«Подставить»** — скопировать выбранный текст в `prompt_edit` главного окна и закрыть (или оставить) диалог.
5. После успешного улучшения — автоматически открыть `PromptAssistantDialog`.

---

### Этап 13.5. Логирование и история (опционально)

1. Записывать запрос ассистента в `request_logs` из **главного потока** после завершения worker.
2. *(Опционально)* не сохранять улучшения в `prompts` автоматически — только по явному действию пользователя («Подставить» → «Отправить»).

---

### Этап 13.6. Тестирование

1. Пустой промт → предупреждение, запрос не уходит.
2. Корректный промт → JSON парсится, все секции заполнены.
3. Модель вернула невалидный JSON → fallback на сырой текст.
4. Нет API-ключа / модель не выбрана → кнопка неактивна или сообщение об ошибке.
5. «Подставить» → текст попадает в поле ввода, можно сразу нажать «Отправить».
6. Повторное нажатие «Улучшить промт» во время загрузки — игнорируется.

---
